## 三、方案比较

1. 推荐：在现有交付快照中增量记录资产引用与镜头来源，沿用现有按钮；不改布局和生成链路。能先形成可追溯记录，但不能一次解决云端素材永久保留或完整版本管理界面。
2. 只导出独立清单：改动更小，但节点和资产库内的成果缺少同一份内嵌记录，追溯容易断开。
3. 新建统一影片工作台与全局资产版本服务：能力更广，但涉及界面、数据库、共享模块和迁移，违反本轮不改变现有设计及工具的边界，不采用。

## 四、首项：交付快照的资产与镜头引用记录

### 用户操作

仍从原有入口选择素材、编辑导演台，点击原有“生成预演节点”、下载或保存至资产库。该项仅增强成果里的引用记录，不增加操作步骤、不自动批准结果，不改变现有 MP4 导出按钮的含义或文件类型。

“生成预演节点”代表用户保存当时状态，不等同最终质量审核通过。完整审批和版本比较界面不是首项交付范围。

### 数据行为

- 沿用现有交付包的主字段，增加独立、带版本标识的可选追溯信息；旧交付包缺失该信息仍能使用。
- 快照仅记录当前项目已使用的资产 ID、reference ID、来源、用途及可取得的版本信息，不扫描其它项目或账号。
- 有可信版本/摘要时记录；无可信内容版本时明确记为未验证，不从文件名、URL 或本地时间伪造版本。首项不下载全部素材计算摘要，也不另建云端备份服务。
- 以现有 MasterTake 为连续镜头基础；只有实际启用的多机位切点才划分相机区间。节拍仅作为时间标记保留，不因节拍自动切镜头。
- 区间引用当前场景的资产集；没有实体级人物资产映射时，标记为场景/区间级引用，不猜某张图对应哪名演员。
- 保留场景确认状态、镜头轨道、人物轨道、灯光版本和批注来源，不更改任何运动采样与渲染结果。
- 新成果携带当时的独立引用快照，后续编辑不改变旧包；不冒称旧包包含的远端素材已被永久保存。

### 集成路径

现有导演状态 -> 交付快照构建 -> 附加引用清单 -> 现有节点/下载/资产回调。

首选修改仅限 spatial-previs 下的交付辅助逻辑及测试。实施计划必须继续核查现有节点、资产保存及恢复调用是否无损保留附加信息；若需要改数据库、共享生成链路或锁定界面，停止扩大范围并明确报告，不能以局部单元测试代替接通。

### 异常与兼容

- 旧数据没有版本：照常工作，追溯状态为未验证，不伪造成功。
- 无法建立引用关系：记录未解析状态，不能静默绑定另一资产。
- 新清单不作为下载或生成的强制质量门槛，不因未验证版本阻止用户原有操作。
- 现有保存/导出失败路径维持原行为，不清空工程，不自动触发视频任务。
- 禁止在追溯信息中写入密钥、令牌或其它账号数据；临时签名 URL 不作永久身份或比较依据。

## 五、验证条件

1. 单元测试先失败再通过：快照隔离、旧包兼容、缺失版本、无切点、有切点、停用多机位、资产未映射、灯光版本保留。
2. 调用链验证：生成节点、下载和保存到资产沿用原入口，记录被真实保留并可读回；仅验证 helper 不算首项完成。
3. 操作回归：原有轨道编辑、LIVE、播放、确认场景及导出仍可用；预演画面不因附加元数据改变。
4. 布局对比：同一项目与视口下，新增前后工具位置、尺寸、默认可见内容一致。
5. 执行 `pnpm experience:check`、相关定向测试、web TypeScript 和构建检查；区分既有失败与本次回归，不掩盖失败。
6. 本地完整试用后提供证据。涉及登录或线上保存的阻塞明确说明，不能把未跑的路径标为通过。

## 六、其余四项顺序

在每项明确设计与现有代码差异后实施，不把五项合并成一次大规模重构。

2. 参考包完善：在现有节点、下载和导出上补齐镜头表及关键帧来源；现有视频格式和入口不变。
3. 原创光影配方：基于已有灯光工具与版本数据补配方、适用条件和校准，不重复添加灯光面板。
4. 连续性检查：复用现有审片批注与对比工具；先做三维计划可确定的规则，模型推断单独标注。
5. 单镜头修订：优先复用现有快照、区间及批注，保留已批准成果；不承诺第三方生成式修复像素不变。
